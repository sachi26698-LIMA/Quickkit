# Administrator recovery: release blockers

This PR is not approved for production until real isolated end-to-end and security checks pass.

- Production recovery uses the fixed apex origin only on Vercel production; preview and local development require their own explicit origin. Preview must use a separately approved HTTPS origin, isolated Supabase project and exact callback allowlist entry. Requests on any other origin fail closed. The browser that requested recovery must open the email link because PKCE verifier cookies are host- and browser-bound.
- The request path uses the existing shared, atomic submission limiter RPC for separate HMAC-derived IP and email buckets (four attempts per 15 minutes each). Its IP bucket is checked first. Missing IP, credentials or storage causes a 503. The ingress must be confirmed to overwrite `x-real-ip` and the service-role RPC must be available before enabling recovery; otherwise throttling may be bypassed or recovery unavailable. Email buckets allow targeted temporary denial of recovery; review operational mitigations.
- A two-second minimum response time reduces obvious timing differences. It is **not** a complete timing-enumeration defense: a slower upstream provider call can exceed the padding, and response distributions have not been measured. A bounded, membership-independent response design and realistic timing tests are still required before release. Do not claim enumeration is eliminated.
- Proof and cookies are cleared after update; that alone does not establish atomic server-side one-time session consumption if a stolen proof and token are replayed. Verify actual Supabase token invalidation and concurrent update behavior, and implement durable atomic consumption if needed before release.
- The automated invalid/expired/reused tests use simulated provider errors. They do not demonstrate real email delivery, expiry, replay rejection, password update, or subsequent login. Test with an authorized isolated administrator and mailbox, never production users.
- Vercel preview protection and the sandbox network restriction have prevented actual deployed-browser testing. Do not weaken these protections to obtain a passing check.
