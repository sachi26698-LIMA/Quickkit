## Executive summary

The most consequential confirmed technical defect was not a missing title, robots directive, sitemap entry, or client-rendered page. A live `word-counter` maintenance override (`enabled: true`, reason `Hiii`) caused `app/(public)/tools/layout.tsx` to call `cookies()` through administrator-session verification. That request-time dependency opted the whole `/tools` route segment—including the tools directory and every tool landing page—out of static/ISR rendering. Production build telemetry showed these URLs as Dynamic (`ƒ`) with private/no-store responses. **Fixed in code:** the layout no longer reads request cookies; admin preview is checked only in the browser on a maintenance-gated tool, through a minimal same-origin endpoint; the layout now revalidates every 300 seconds. The live Supabase row was deliberately not changed.

A confirmed 308 was also added from the literal Search Console URL `/tools/words-to-pdf` to the canonical `/tools/word-to-pdf`. The existing `/copyright` → `/intellectual-property` 308 remains correct.

No code change was made to manufacture sitemap `<lastmod>` values for shallow clones. The implementation and tests intentionally omit an unverified date rather than fabricate a timestamp or fall back to filesystem mtime. The existing JSON-LD `SearchAction` is retained: the site has a real `/tools?q=` search, and its query URLs intentionally receive `X-Robots-Tag: noindex, follow` and a clean `/tools` canonical. `/category/ai-tools` remains intentionally `noindex, follow` and excluded from the XML sitemap.

The rest of the GSC outcomes are principally indexing-selection / content-quality decisions, not crawl blocks. All indexable categories and tools are linked from the home/category/tool directories or the HTML sitemap, and the XML sitemap derives eligible routes from the published catalog and canonical/indexable rules. Google can still choose not to index a URL; a sitemap or `Request indexing` is not a guarantee.

## Cross-cutting technical findings

### Rendering, maintenance and cacheability

- Before the fix, `ToolsLayout` awaited `isSignedInAdministrator()`, which read request cookies and called `verifyAdminSession()`. With the active `word-counter` maintenance override, the production build treated `/tools`, `/tools/[calculator]` and all dedicated `/tools/*` landing pages as Dynamic; the affected pages could return private/no-store responses. This connected the one active maintenance flag to every tool landing route, not just the switched-off tool.
- `app/(public)/tools/layout.tsx` now reads only the public catalog, projects active notices, and exports `revalidate = 300`. It contains no `next/headers` import or `cookies()` call. `ToolMaintenanceGate` calls same-origin `GET /api/admin/session` only when a maintenance notice exists for the visited tool; cookie values are not read or serialized in client code. The endpoint returns only `{ authorized: boolean }` and uses `private, no-store` plus `Vary: Cookie`; it never returns an admin email or identity. This remains within CSP `connect-src 'self'`, and no browser-side Supabase SDK or host was introduced.
- Regression coverage simulates a catalog with an active maintenance notice and proves it is still passed to the gate without request cookies. The gate tests ordinary visitors and admin preview; the CSP test passes.
- Production build after the fix lists `/tools`, the generic calculator segment and all listed dedicated tool routes as static (`○`) or statically generated (`●`), with 5-minute revalidation. `/api/admin/session` is correctly Dynamic (`ƒ`) as an authenticated, no-store endpoint.
- Scope respected: the live `word-counter` Supabase override (`reason: "Hiii"`) was not changed.

### Metadata, robots, canonicals, redirects and sitemap

- Public route metadata is generated through shared builders/SEO records (`lib/seo.ts`, `lib/seo/resolve.ts`, `lib/seo/tools.ts`, `lib/seo/pages.ts`). The audited indexable GSC pages use index/follow and self-canonicals; their XML sitemap inclusion is derived from catalog publication, `isIndexable`, canonical path, and SEO-registry exclusions.
- `/category/ai-tools`, query-filtered `/tools` URLs, `/saved`, `/qr`, admin pages and selected utility routes carry intentional noindex behavior. Do not “fix” those by broadening indexing.
- `/copyright` already 308-redirects to `/intellectual-property`. `/tools/words-to-pdf` now 308-redirects to `/tools/word-to-pdf`. Redirect sources must not appear in the sitemap; the destination pages have their own canonicals.
- `app/robots.ts` allows public crawling, disallows `/api/`, points to `/sitemap.xml`, and does not block noindex URLs from being fetched. On unapproved previews it disallows the site except `/ads.txt`; this is gated by `SITE_URL`, `LAUNCH_APPROVED`, and deployment environment.
- XML sitemap contains eligible canonical URLs only (the regression suite verifies all 80 eligible routes, no redirects/noindex/duplicate URLs). `/sitemap` is a separate HTML directory listing all indexable categories/tools and many informational pages.
- `<lastmod>` is based only on real Git commit dates for route-owned source files. On a Vercel shallow clone the only reachable commit may be the shallow boundary, so the date can be omitted. `tests/launch.test.ts` explicitly requires omission when no independently verifiable history exists and rejects wall-clock, mtime, arbitrary cutoff, and fabricated fallback dates. **No fix recommended in application code:** omitted `<lastmod>` is preferable to false freshness. If dates are operationally required, configure the build checkout/history depth rather than inserting synthetic dates.

### SearchAction, structured data, CSR/SSR and page quality

- Keep `WebSite.potentialAction` `SearchAction`: it points to the actual `/tools?q=` search pattern. Google may discover a literal template-shaped URL through JSON-LD; it is not a page intended for indexing. Query URLs get `X-Robots-Tag: noindex, follow` and canonicalize to `/tools`.
- Tool and category explanations, titles and metadata are server-rendered. Interactive search/filter grids are client components, but SSR HTML includes their crawlable tool links and explanatory content; indexing does not depend solely on client-side discovery. `CollectionPage`/`ItemList` appears on `/tools` and populated categories; `BreadcrumbList` mirrors visible breadcrumb navigation; tool pages use WebApplication/HowTo/FAQPage where applicable. No unsupported ratings/reviews were observed. Existing structured-data tests cover these behaviors.
- The audited category pages have roughly 490–902 words. The affected tool pages range from about 567 to 2,133 words; the low-end developer utilities/calculators are the strongest candidates for genuine, task-specific enrichment. Word count is not a ranking target: add examples, edge cases, accurate limitations and a useful workflow, not boilerplate or doorway copy. Help/sitemap/policy pages should be assessed for actual user need rather than forced into the index.
- Internal-link audit found no orphaned indexable categories/tools: routes have links from homepage/category directories, `/tools`, related links and/or the HTML sitemap. Most category routes have broad home/navigation reach; individual affected tools typically have about 4–12 contextual inbound links, `/batch-code-checker` has 66 from brand pages, and the HTML sitemap links every indexable tool. Existing coverage tests assert zero orphaned indexable routes. No broad footer-link change was justified (the legal-page tests specifically preserve `data-home-link="hidden"`).

### Headers, CSP and service worker

- `next.config.ts` sends `X-Robots-Tag: noindex, follow` for `/tools` requests with `q` or `category` query parameters and a separate intentional `noindex, follow` rule for `/category/ai-tools`. Preview/development can get site-wide noindex when indexing approval is off; ensure the production build has `SITE_URL=https://quickkit-rosy.vercel.app` and `LAUNCH_APPROVED=true` as in the verified build.
- Production CSP is enforced; `connect-src` includes `'self'` and documented advertising hosts, not a Supabase API origin. The maintenance preview call is same-origin. Other response protections include HSTS, `nosniff`, and strict-origin referrer policy. No indexing defect was found in the CSP.
- `components/offline-indicator.tsx` registers `/sw.js`; the worker supports offline UX. It is not the source of the noindex states or the prior Dynamic rendering bug. The explicit offline route is itself noindex. No service-worker indexing change was justified.

## Changes made

1. `next.config.ts`: permanent 308 `/tools/words-to-pdf` → `/tools/word-to-pdf`.
2. `app/(public)/tools/layout.tsx`: removed request-time administrator-cookie/session checks and added `revalidate = 300`.
3. `components/tool-maintenance-gate.tsx`: performs a same-origin admin session probe only for an active maintenance dialog and cookie-present browser; preview controls require a successful response whose JSON explicitly has `authorized: true`.
4. `app/api/admin/session/route.ts`: no-store, Node runtime route exposing only an authorization boolean.
5. Regression tests in `tests/sitewide-indexing-seo.test.tsx`, `tests/tool-maintenance-gate.test.tsx`, `tests/tool-maintenance-layout.test.tsx`, and `tests/admin-session-api.test.ts`.
